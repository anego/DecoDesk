# 1. ログ出力の基本方針
* **ロギングフレームワークの使用:** `Console.WriteLine` などの標準出力は使用せず、必ずプロジェクトで指定されたロギングインターフェース（例: `ILogger<T>`）を使用すること。
* **構造化ログの推奨:** ログメッセージ内に変数を文字列結合（`$` による補間など）で埋め込むのではなく、構造化ログ（`_logger.LogInformation("Processing file {FileName}", fileName);`）の形式を使用すること。

# 2. ログレベルの厳格な使い分け
ログを出力する際は、以下の基準に従って適切なレベルを選択すること。

* **Trace / Debug (開発・デバッグ用)**
  * 用途: 開発中の動作確認、変数の状態、詳細な関数の入出力、ループ内の個別処理など。
  * 例: "画像のメタデータ抽出を開始: Width=1920, Height=1080"、"DBクエリ実行時間: 15ms"

* **Information (業務記録・状態遷移)**
  * 用途: アプリケーションの正常な状態変化、主要なプロセスの開始・終了、設定の変更など、運用側がシステムの稼働状況を把握するための情報。
  * 例: "アプリケーションを起動しました"、"ディレクトリ [Path] のインデックス作成が完了しました (150件)"

* **Warning (警告・復旧可能な異常)**
  * 用途: エラーには至らないが注意が必要な状態、デフォルト値へのフォールバック、リトライが発生した事象など。
  * 例: "設定ファイルが見つからないため、デフォルト設定を適用します"、"ファイル [Path] の読み込みに失敗したためスキップしました"

* **Error (業務エラー・例外)**
  * 用途: 特定の処理や機能が失敗し、継続できない状態。キャッチした例外（Exception）は必ずこのレベルで記録すること。
  * 例: "データベースへのバルクInsertに失敗しました"、"画像 [Path] のレンダリング中に例外が発生しました"

* **Critical / Fatal (致命的なエラー)**
  * 用途: アプリケーション全体がクラッシュする、または強制終了せざるを得ない致命的な障害（DBのファイル破損、メモリ枯渇など）。
  * 例: "SQLiteデータベースファイルにアクセスできないため、アプリケーションを終了します"

# 3. ログ記述時の禁止事項
* 個人情報やセキュリティに関わる機密情報（パスワード、トークンなど）をログに出力してはならない。
* 意味のない不要なログ（例: "ここを通過しました" のような一時的な記述）はコミット前に削除すること。
